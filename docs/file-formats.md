# File formats

All files are UTF-8 text with `\n` line endings. Game-side files live under
`cstrike/addons/sourcemod/data/tasurf/`:

```
data/tasurf/
  baked/   <name>.tas            baked timelines (written by the baker / install)
  starts/  <name>.json           start states (written by tas_setstart)
  runs/    <name>_NNN.csv        one file per run (written by the plugin)
           <name>_NNN.meta.txt   run metadata, not part of the determinism check
           <name>.preview.csv    the latest fast preview (same format; host_timescale shows in its header)
  requests/ request.txt          run request from the browser editor (taken and deleted by the plugin)
           <id>.result           the plugin's answer: status, csv, detail
           heartbeat.txt         the plugin's state, rewritten about once a second
           draw.txt              which run CSVs the game should draw (kept in place)
  tasurf.log                     one line per run, plus setting changes
```

On a map without a bot navigation file, the plugin also writes `cstrike/maps/<map>.nav`
(a minimal version 16 mesh with one area) so the replay bot can join; see
[design.md](design.md#the-replay-bot-built).

## Editor requests (`requests/`)

`request.txt`, written by the editor atomically (write `request.tmp`, rename):

```
id 3f2a9c81d0e4
load surf_beginner_edit.preview
preview
```

The last line is `run` (normal speed, a numbered run CSV), `preview` (sped up,
`runs/<name>.preview.csv`), or `record <tick>`: the timeline plays you to that tick,
then you're recorded (`<name>.record.tas`; the recording is saved as
`baked/<name>_from<tick>.tas`). The editor replaces a pending `preview` with a newer
request; a pending `run` is never replaced. The plugin takes the file by renaming
it to `request.taken`, then plays it and answers in `<id>.result`:

```
status complete
csv surf_beginner_edit_004.csv
detail vs surf_beginner_edit_003.csv: first divergence at tick 812: ...
```

`status` is the run status (`complete`, `stopped by tas_stop at tick N`, ...),
`preview` for a finished preview, `recorded ...` for a recording, `cancelled` (a
recording stopped before your turn), `error` (detail says why), or `superseded`
when a newer request replaced a preview that was still playing. `baked <name>`
(0.8) names the baked file the plugin had loaded at the end: for a recording,
the recording itself.

`heartbeat.txt` (0.6):

```
version 0.6.0
map surf_beginner
mode edit            edit, record, or off (tas_bot 0)
bot ready            ready, none, adding, dead, reload-map, off
ready no             can a request be played now
why you're in record mode: type tas_mode edit in the game (requests wait until then)
player alive         alive, dead, spectator, none
state idle           idle, preview, running, recording
time 1791657600
```

`why` is only there when `ready` is `no`. The editor treats a heartbeat older
than 5 seconds as "the game isn't running TASurf".

`draw.txt`, written by the editor whenever what should be on screen changes:

```
id 890649f2cbeb
map surf_beginner
path surf_beginner_edit.preview.csv
ghost surf_beginner_edit_003.csv
timeline surf_beginner_edit
cursor 1250
files 3fa9c2d1
```

The plugin draws `path` in speed colours and `ghost` (or `-`) thin and grey,
once per new `id`, while no run is playing, and only on that map. `cursor` is
the tick selected in the editor (or `-`): `path` is drawn red up to it, white
for one second of ticks after it (the tickrate, 67 at 66.67), with a yellow post
on it. `timeline` is the editor's timeline, so the plugin's own drawing after a
run or preview of it uses the cursor too. The plugin keeps the CSVs loaded
while only the cursor moves; `files` changes whenever the CSVs do (file times
in SourceMod have whole seconds only, and previews can be quicker). The file
stays in place, so after a plugin reload or a map change the same paths are
drawn again.

## Baked file (`.tas`), version 1 (2 with auto-strafe)

Produced by `python -m tasurf bake`. Don't edit it by hand: edit the timeline
and re-bake. The plugin re-reads it on every `tas_run`.

```
# TASurf baked timeline, generated by `python -m tasurf bake`.
# Edit the timeline JSON and re-bake; do not edit this file by hand.
@format tasurf-baked 1
@name example_surf
@hash f285cf775639c6e2
@map surf_beginner
@ticks 330
@setting tickrate 66.6667
@setting sv_airaccelerate 150
@start origin -64.000000 3616.000000 -31.000000
@start origin_bits C2800000 45620000 C1F80000
@start angles 0.000000 180.000000 0.000000
@start angles_bits 00000000 43340000 00000000
@start velocity 0.000000 0.000000 0.000000
@start velocity_bits 00000000 00000000 00000000
@start base_velocity 0.000000 0.000000 0.000000
@start base_velocity_flag 0
@start on_ground auto
@start ground_entity 0
@start ducked 0
@start gravity 1.000000
@start lagged_movement 1.000000
@start velocity_modifier 1.000000
@start stamina 0.000000
tick,yaw,pitch,forwardmove,sidemove,buttons
0,-180.000000,0.000000,400.000000,0.000000,8
1,-180.000000,0.000000,400.000000,0.000000,8
...
```

* `#` lines are comments. `@` lines are the header, with single spaces between
  tokens. The `tick,...` line names the columns.
* Tick lines: `tick,yaw,pitch,forwardmove,sidemove,buttons`. Ticks are
  consecutive from 0, and there are exactly `@ticks` of them. yaw is wrapped to
  (−180, 180], the range the CS:S client sends. Values have 6 decimals, more when needed to give back
  the exact float32 the plugin uses. buttons is the IN_* bitmask.
* Recordings (`tas_record`) add four columns:
  `yaw_bits,pitch_bits,forwardmove_bits,sidemove_bits`. These are the exact float32
  bits of what you sent, and they take precedence over the decimals. A recorded
  yaw isn't wrapped.
* `@strafe <from> <to> <offset>` (version 2 and later): ticks `[from, to)` are
  auto-strafe (see [timeline-format.md](timeline-format.md#strafe)); their
  tick lines' yaw is the fallback for ground ticks. The baker writes version 2
  only when there is a strafe range, so other files and their hashes are as
  before. Plugins older than 0.7 refuse version 2.
* `@strafe <from> <to> <offset> <heading>` (version 3 and later): a straight range. The
  plugin also picks A or D each tick (the sidemove's sign and the A/D button bits)
  to keep going `heading`. The baker writes version 3 only when there is a
  straight range; plugins older than 0.11 refuse it.
* `@strafe <from> <to> <offset> <heading> <swing>` (version 5): a straight range that
  swings: the plugin keeps the side it played the tick before until the direction is
  `swing` degrees past the heading. The baker writes version 5 only when there is
  one; plugins older than 0.13 refuse it.
* `@strafe <from> <to> <offset> <heading> <swing> <gain>` (version 6): a swing that turns
  smoothly, keeping `gain` percent (75 to 100) of the most speed gain. The plugin sets
  forwardmove and sidemove (some W, and A or D) and looks along the velocity. Plugins
  older than 0.14 refuse it.
* `@autobhop` (version 4 and later): auto bhop. On a tick that starts in the air (not on a
  ladder, in water or in noclip) the plugin lets go of a held jump, so a tick that
  starts on the ground with jump held jumps (CS:S only jumps when jump wasn't held
  the tick before). It changes the run, so it's hashed. The baker writes version 4
  only for a timeline with `"autobhop": true`; plugins older than 0.12 refuse it.
  Run CSVs and recordings hold the buttons as played, jump let go in the air.
* `@view_pitch <first tick> <pitch>...` (after the tick lines, only when the
  timeline has a `view_pitch`): up to 16 values a line, 2 decimals, covering every
  tick in order. What replays show on the bot's eyes; the movement still uses the
  tick lines' pitch. Plugins older than 0.9 refuse these lines.
* `@view_yaw <first tick> <yaw>...` (after the tick lines and any `@view_pitch`
  lines): the camera replays show on those ticks, up to 16 values a line, 4 decimals,
  one line for each run of consecutive ticks (or more, 16 at a time); other ticks
  show the yaw played. The editor writes them for auto-strafe ranges (or the whole run:
  the timeline's `camera_smoothing`) once the game
  has played the same inputs (`tasurf/camera.py`: that path's yaw smoothed with the
  ticks either side), and only for plugins 0.15 and later, which put them on the
  replay's eyes; older ones refuse these lines. The movement still uses the yaw
  played.
* `@hash` identifies "the same timeline": the plugin only compares runs with
  equal hashes. It covers every non-comment line except the `@hash` line
  itself and the `@view_pitch` and `@view_yaw` lines, each followed by `\n`. The baker writes the first 16 hex digits of
  its SHA-256. The plugin, which has no SHA-256, writes recordings as
  `fnv1a32:xxxxxxxx` (FNV-1a 32 over the same lines). `read_baked` checks either.
* `@start *_bits` are exact float32 bit patterns, and the plugin uses them
  instead of the decimals. The baker always writes them, either from the
  capture or computed from the decimal.
* Optional `@start` keys: `view_offset_z`, `health`, `maxspeed`. When
  `velocity_modifier` or `stamina` are missing, the plugin uses 1 and 0; the
  baker always writes them.
* Unknown `@` keys are errors (the plugin and the baker change together).

The parser is implemented twice, in `plugin/scripting/tasurf/baked.sp` and as
`read_baked()` in `tasurf/bake.py`; the tests use the Python one to check the
baker's output.

## Start file (`starts/<name>.json`)

Written by `tas_setstart`. It has exactly the shape of a timeline's `start`
object (see [timeline-format.md](timeline-format.md#start)):

```json
{
  "format": "tasurf-start",
  "version": 1,
  "map": "surf_beginner",
  "origin": [-63.968750, 3615.968750, -31.968750],
  "origin_bits": ["C27FE000", "4561FF80", "C1FFC000"],
  "angles": [4.312500, 179.428711, 0.000000],
  "angles_bits": ["408A0000", "43336DC0", "00000000"],
  "velocity": [0.000000, 0.000000, 0.000000],
  "velocity_bits": ["00000000", "00000000", "00000000"],
  "base_velocity": [0.000000, 0.000000, 0.000000],
  "base_velocity_flag": false,
  "on_ground": true,
  "ground_entity": 0,
  "ducked": false,
  "view_offset_z": 64.000000,
  "gravity": 0.000000,
  "lagged_movement": 1.000000,
  "velocity_modifier": 1.000000,
  "stamina": 0.000000,
  "health": 100,
  "maxspeed": 260.000000
}
```

(The values above are illustrative, not from a real capture.)

## Run CSV (`runs/<name>_NNN.csv`)

`NNN` is the first unused run number. Header lines are `# key value` with
unique keys, then one column line, then one row per tick:

```
# tasurf-run 1
# plugin_version 0.1.1
# name example_surf
# baked_hash f285cf775639c6e2
# map surf_beginner
# ticks_planned 330
# ticks_recorded 330
# status complete
# settle_ticks 1
# tick_interval 0.015000
# tick_interval_bits 3C75C28F
# tickrate 66.6667
# cvar.sv_gravity 800
# cvar.sv_airaccelerate 150
# ...                                  (fixed list of movement convars; <missing> if absent)
# player.maxspeed 260.000000
# start.origin -64.000000 3616.000000 -31.000000
# start.origin_bits C2800000 45620000 C1F80000
# start.angles 0.000000 180.000000 0.000000
# start.velocity 0.000000 0.000000 0.000000
# start.velocity_bits 00000000 00000000 00000000
# start.base_velocity 0.000000 0.000000 0.000000
# start.on_ground auto
# start.gravity 1.000000
# start.lagged_movement 1.000000
tick,yaw,pitch,forwardmove,sidemove,buttons,x,y,z,vx,vy,vz,hspeed,on_ground,ground_entity,ducked,base_vx,base_vy,base_vz,x_bits,y_bits,z_bits,vx_bits,vy_bits,vz_bits,yaw_bits,pitch_bits
0,-180.000000,0.000000,400.000000,0.000000,8,...
```

Row `t` holds:

* the inputs the engine **actually processed** for tick t (read back after the
  command ran, so another plugin changing inputs would show up here);
* the player's state **after** the engine finished tick t: origin (feet),
  velocity, horizontal speed `sqrt(vx² + vy²)` (computed in float32), ground
  flag, ground entity (−1 airborne, 0 world), duck flag and base velocity;
* `*_bits`: the exact float32 bits of origin and velocity, so a text comparison
  is a bit-exact comparison, and (0.7 and later) of the yaw and pitch played,
  which on auto-strafe ticks the plugin chose itself.

The state before tick 0 is the start state in the header.

`status` is `complete`, or e.g. `stopped by tas_stop at tick 120`,
`aborted: player died at tick 87`. If convars changed during the run, a line
`# warning settings_changed_during_run ...` is added (the `cvar.*` values are
from tick 0).

The CSV holds nothing that varies between identical runs: no timestamps, no
command numbers, no paths. Two runs of the same baked file with the same
settings and `tas_settle_ticks` must give byte-identical CSVs.

## Run metadata (`runs/<name>_NNN.meta.txt`)

`key value` lines: date, status, baked file path and hash, the user-command
number and server tick at tick 0, the number of commands the engine dropped
(the timeline waits for these, so they don't affect the result), the settle
ticks used, the result of the in-game comparison with the previous run, and the
plugin and SourceMod versions. Send these along with CSVs when reporting a
problem.
